### The three QA blockers owned by the Coder — check each by hand

**BLOCKER 1 — the worst one. REPORTED FIXED by the Coder, not yet re-audited by QA.** Node `IF - Was The Brief Approved?` read the approval result at
`$('Telegram - Request Brief Approval').item.json.approved`. n8n's official approvals
documentation puts it **under `data`**:

```json
{ "data": { "approved": true, "respondedAt": "2025-07-13T12:34:56.000Z", "responder": {} } }
```

So the original expression was always `undefined === true`, always false. **Leo taps Approve, the
workflow decides he did not, no email is sent, and the execution finishes green.** The prescribed

```
={{ ($('Telegram - Request Brief Approval').item.json.data?.approved ?? $('Telegram - Request Brief Approval').item.json.approved) === true }}
```

### The HubSpot dispute, and how it was settled — read this before trusting any single agent

`additionalFields.properties` does not exist. **QA was wrong. The Coder refused the fix and was

instance, 2026-09-13:

- **`sortBy` exists at exactly one path in the whole 87-property schema: `additionalFields.sortBy`.**

**Acceptance criterion 4 is amended** to require the properties at `additionalFields.properties`.

**The lesson.** QA was right to challenge the node. The Coder was right to refuse a fix it could

### Node schema traps, all read from this instance's schemas

- **Gmail `sendAndWait` cannot attach a file.** The attachments field exists only under
  `operation: send` and `operation: reply`. It is absent from `sendAndWait`. So an approval email
  can carry a link and nothing else. This is why Telegram was chosen for approval.
- **The Google Docs node cannot insert an image at all.** It offers only create, get and update on
  a document. Confirmed twice — by the Designer and by hand in the main session. This is why the
  brief is built as HTML and uploaded to Drive for conversion.
- **The OpenAI node has no built-in model list.** `@n8n/n8n-nodes-langchain.openAi` holds `modelId`
  as a resource locator whose "From List" calls the OpenAI API through the credential. A model id
  typed from memory will not fail validation — it will fail at run time, after the call is billed.
  **Pick the model id from the live list.**
- **HubSpot deal search returns bare deal IDs by default.** The node's own description says so. The
  properties field is at **`filters.properties`**, NOT `additionalFields.properties` — the Coder
  got this wrong first time and QA caught it. `additionalFields` for `deal:search` holds only
  `sortBy`, `direction` and `query`.
- **HubSpot filter operators `GT`, `GTE`, `LT`, `LTE` only exist when `type` is `number`.** Under
  `type: "string"` the options are `CONTAINS_TOKEN`, `EQ`, `HAS_PROPERTY`, `NOT_HAS_PROPERTY`,
  `NEQ`. The Coder paired `GTE` with `type: "string"`, which the schema does not offer.
- **The Supabase row limit defaults to 50.** Left at the default it silently truncates. Its
  `orderBy` description warns: "Recommended when using Return All or Limit ≥ 1000 to avoid
  duplicate or missing records."
- **Telegram `sendMessage` caps at 4,096 UTF-8 characters** and returns a hard
  `400 Bad Request: message is too long`. It does not truncate.
- **Merge v3.2 `output: empty` is real.** Confirmed in the schema, labelled "A Single, Empty Item",
  offered only with `mode: chooseBranch` and `chooseBranchMode: waitForAll`. **But what it does at
  runtime when an input carries an error-shaped item or zero items is UNPROVEN.**
